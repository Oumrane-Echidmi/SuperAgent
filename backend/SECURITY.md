# Identity slice: trust boundaries and limits

Connected Docs, Company Brain, Agents and Workflows use `workspace_records` with forced tenant row policies. Members read; owners create/edit/archive. Immutable creation IDs bind normalized intent; updates lock/check revisions before changing explicit mutable columns. Strict kind-specific schemas bound text/graphs and reject injected actor, tenant and execution fields. Agent model choices are checked against the configured API allowlist. Saving a record grants no workflow execution, publication, AI retrieval or external-message authority. Inbox lists existing tenant-isolated conversations and filters linked order attempts by both tenant and conversation. No new public data endpoints or provider calls are introduced. See [WORKSPACE_FEATURES.md](../WORKSPACE_FEATURES.md) for storage and retry semantics.

HTTP bodies, bearer headers and tenant IDs are untrusted. Strict Zod schemas bound fields; SQL values use parameters. The API derives user identity only from a live session digest, then sets transaction-local `app.user_id` on one pooled connection. Tenant context is never accepted from a client header. PostgreSQL policies restrict tenant reads, membership reads, and profile reads/writes. Runtime SQL credentials are trusted service credentials, never client credentials: arbitrary SQL access could set application context directly.

Migrations run with `ADMIN_DATABASE_URL`. The API uses `DATABASE_URL` as the non-owner `superagent_app` login, which has no superuser/BYPASSRLS privileges or role memberships. Startup rejects privileged/owner credentials. The migration role is deliberately privileged and must never serve HTTP. Policies are forced on tenant tables, and grants exclude schema changes, tenant deletion and membership mutation. Platform identity tables (users, sessions and auth counters) are available to the trusted backend for credential verification, not tenant API queries. Responses expose explicit field allowlists.

Abuse cases covered by tests include guessing another tenant's UUID, injecting membership claims, staff editing owner fields, reusing expired/revoked tokens, leaking pooled context, and concurrent rate-limit increments. Invalid credentials return a generic response; unknown accounts perform a dummy scrypt derivation. Account registration conflicts may reveal that an address is registered. Email ownership verification is not implemented; do not expose signup publicly yet.

Passwords use salted scrypt (N=32768, r=8, p=3, 64-byte output). Opaque 256-bit bearer sessions expire after 24 hours. Only SHA-256 token digests persist. Authentication endpoints share PostgreSQL rate counters and each process caps concurrent scrypt derivations at four. The server serves no cross-origin browser credentials and does not enable CORS. Responses use no-store on identity routes, nosniff, frame denial and restrictive CSP. Terminate HTTPS before any public deployment and configure HSTS on that HTTPS boundary.

Data classification: email is personal data used for login; password hashes and session digests are sensitive authentication data; tenant name and profile text can contain business or personal data supplied by an owner. Do not put customer messages or payment data in these fields. Auth counter keys are SHA-256 hashes of IP/email and retained for the active 15-minute window plus cleanup lag. Sessions persist until expiry/revocation plus cleanup lag. Run the cleanup command every 15 minutes. Account/profile data lasts until the development account is removed; no public retention/deletion claim is made by this slice. Before onboarding real shops, implement verified account recovery, deletion/export, explicit retention, audit events, backup retention/recovery and production TLS/proxy controls.

Local database volume persists across container restarts. Never use production data for the integration suite. The suite removes only its generated fixtures; it does not drop schemas or truncate tables.

Catalog access is a separate platform role stored in `platform_admins`, granted only through privileged maintenance. The runtime can read its current user's grant but cannot insert or delete grants. Catalog draft writes and audit appends require that role in both HTTP and PostgreSQL policies. Signed-in users can read released snapshots, never drafts or audit records. Runtime credentials have no UPDATE/DELETE privileges on releases or audit rows. Original creation definitions persist to distinguish safe creation retries from UUID reuse after edits. Drafts, release snapshots and audits are platform-owned catalog records retained until privileged maintenance removes a scenario; use synthetic fixtures and never include credentials or real customer messages. Audit records store actor IDs and are available only to platform admins. Before public deployment, establish catalog retention and offboarding rules alongside account deletion.

Scenario integration tests temporarily revoke the runtime audit INSERT grant to verify atomic rollback, restore it in `finally`, and run serially in the dedicated test database. Do not run these tests against live traffic. They also cover repeated/concurrent releases, stale edits, failed fixture gates, tenant-owner denial, role self-promotion denial and SQL-level immutability.

Builder drafts, revisions, simulations and approvals carry tenant IDs and forced row policies. Members can read; owner membership is required for writes. Platform-admin catalog authority grants no tenant access. Only the draft head's current-revision pointer and update timestamp are mutable by the runtime. Pins, creation intent, revision content and review evidence cannot be updated/deleted through runtime grants. Approval foreign keys bind the exact revision hash and simulator evidence; policies additionally require a current revision and passing report. The API derives actor, hash, fixture suite and simulator version server-side, locks the head before fresh revision reads, and reruns fixtures before approval. Setup intent is untrusted text and is not executed as instructions or sent to an AI/provider in this slice.

Setup goals/names may contain personal or business data. Collect only facts needed for the setup, never credentials or customer messages. History, reports and approvals persist until privileged tenant deletion cascades through the draft records; the API exposes no self-service erase operation yet. Publishing and model integration must define retention/export/deletion behavior before real onboarding. Integration fixtures are synthetic and deleted by their generated tenant IDs. Builder tests temporarily revoke revision INSERT permission to verify that failed appends roll back the head, then restore the grant in `finally`.

Customization is restricted to published enumerated choices for existing literal inputs. Owners cannot supply expressions, change graphs or weaken fixture assertions. The admin release gate tests every allowed combination, bounded to 16; approval hashes include selected values. Parameter fixture references are resolved from declared keys only. The local-1.1.0 review engine applies that resolution to both simulation and approval; earlier engine evidence is retained but cannot approve the current engine.

Matching is deterministic and makes no provider/model calls. User goals cannot register capabilities or edit catalog entries. Matching records are immutable to the runtime and scoped to tenant membership. The explicit exception is platform-admin review of rows whose server-generated state is UNSUPPORTED; supported-candidate records remain tenant-scoped. Admin queue access is checked in HTTP and row policies. Matching results do not approve/publish a workflow. Goals/results are personal/business data collected for scenario selection and catalog-gap review, retained for 30 days plus daily maintenance lag. The maintenance-only cleanup command implements deletion; runtime requests have no DELETE grant. Tenant deletion also cascades these records. The integration suite verifies cleanup removes an expired synthetic request while preserving a current one.

AI Builder chat is separately opt-in at the API/worker and requires owner consent to OpenAI processing per session. Only queued owner messages, same-session successful history and allowlisted released-catalog summaries leave the backend. Model calls have a fixed HTTPS destination, redirects disabled, strict output schemas and bounded input/output/time. Tools default off. An immutable per-session MCP consent flag additionally permits up to four reference-tool calls through operator-configured public HTTPS MCP servers, with explicit name allowlists and the provider's server-declared read-only filter. Review the actual tool behavior and disclose the server list before obtaining consent; annotations and model instructions are not a sandbox guarantee. Get fresh consent in a new session after changing the server list. MCP credentials, local commands and write tools are unsupported. No API key is included in model input or MCP configuration. Unexpected server labels, tool names, approval requests and failed tool outputs are rejected. The worker never reads credentials, profiles, other tenant conversations, graphs or fixtures. Incoming model replies are untrusted: schema, exact scenario pins and allowed setting values are revalidated before storing a proposal. Model data has no authority to create/approve/publish a draft or make an application connector call. Live linguistic/grounding evaluation remains a deployment gate. See [AI_MCP.md](../AI_MCP.md) for setup and data-sharing details.

The API runtime can enqueue but cannot update inference results. A separate non-owner, non-BYPASSRLS worker role can read chat work/catalog and update only processing/result columns. It cannot read users/auth sessions/credentials or access draft/approval tables. Its cross-tenant chat access is a trusted service boundary: history queries explicitly bind tenant/session, and membership checks use the actor from the claimed job. A lease UUID and wall-clock deadline fence completion; expired attempts are terminal and not requeued. The daily 20-request reservation is atomic with enqueue and not refunded for uncertain/failed work. Usage may be unavailable after transport failure/crash; no raw provider diagnostic is persisted or logged.

The frontend model selector uses an authenticated tenant-scoped allowlist. Each selected model is pinned to the durable turn, validated before reserving quota and independently checked by the worker before a provider request. Runtime/worker roles cannot mutate that model after insertion. Explicitly changing the model on a replayed message ID is rejected. Model selection never changes another business's configuration or exposes the API key. Keep API/worker allowlists synchronized when deploying configuration changes.

Chat text, extracted setup facts, provider identifiers and token usage are business/personal data used for setup and diagnostics. Sessions/turns are retained for 30 days from creation plus daily maintenance lag. Cleanup deletes parent sessions and cascades turns; tenant deletion cascades the same data. Platform-admin access is limited to unsupported turn rows for catalog-gap review through an explicit endpoint, with a corresponding row policy; other chat history requires membership. Operator review of unsupported setup goals is part of this data flow. Keep maintenance credentials separate from API and worker deployment environments. Tests use synthetic records and a fake provider; they make no paid OpenAI calls.

COD records are manual staff operations, not verified provider events or model tool calls. Members can read/record their tenant's attempts; no user-supplied tenant, amount total, actor, channel or ownership override is accepted. Item/quantity/customer fields and shop-entered unit/delivery prices are validated; totals use bounded integer minor units. Explicit decision evidence and the exact current summary hash/revision are required. Model Builder workers cannot read/write COD records. No WhatsApp callback or Sheets network request is exposed by this slice.

Attempt content revisions, orders, decision receipts and sheet-sync payloads are append-only to runtime credentials. Pending-only update policies prevent reopening terminal attempts. Deferred foreign keys and one transaction bind a confirmed state, immutable order and decision receipt; the same transaction saves the unique sheet projection intent. Decision UUIDs bind exact parameters globally within the tenant, and order IDs/operation keys are stable across future workflow upgrades. Cross-tenant reads are denied by row policies and API membership checks. The projection remains AWAITING_CONNECTION until a later authorized connector integration; no external effect is claimed or retried here.

Customer contact/address, staff evidence and historical summaries are personal/business data retained for the tenant's operational records. Privileged tenant deletion cascades all COD data and pending local projections. There is no production auto-purge policy or provider-side deletion yet: define shop retention, export, backup and external projection deletion before real customer onboarding. Synthetic integration fixtures exercise missing details, refusal, ambiguous intent, concurrent replay, changed summaries, rollback on sheet-intent failure, staff attribution, terminal immutability, business-timezone metrics and cross-tenant denial. Tests temporarily revoke the runtime sheet-intent INSERT grant, restore it in finally, and run only in the dedicated serial test database.

References: [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [node-postgres transactions](https://node-postgres.com/features/transactions), [parameterized queries](https://node-postgres.com/features/queries).

# Google provider primitives

The credential vault authenticates the tenant, provider and connection as AES-GCM additional data. A caller must authorize that context before decryption. Envelope ciphertext belongs in protected storage; key material belongs in a secret manager with access limited to the connector service. Keep old keys only while migrating retained envelopes. A missing key, tampering or wrong context returns the same safe error. Google OAuth setup now persists encrypted credentials; a delivery worker remains unimplemented.

The Google protocol adapter uses fixed HTTPS origins, rejects redirects and bounds response sizes and deadlines. RAW string cells avoid interpreting customer text as formulas. Provider errors never include response bodies or request secrets. A successful append is validated against its destination and row dimensions. A dispatched request with uncertain outcome is never retried by the adapter; future orchestration must persist and reconcile it using the stable order identity. Do not invoke append directly from a request handler or inside an order transaction.

Google setup is opt-in, owner-only and protected by owner-only forced RLS; the Builder worker has no connection-table privileges. The API derives the user from a live bearer session and uses an explicit metadata allowlist. Strict request schemas disallow client credentials, scopes, redirect overrides and account claims. Random 256-bit state persists only as a SHA-256 digest. PKCE verifiers are encrypted using a distinct `connectionId:pkce` context; refresh tokens use the connection ID itself, so envelopes cannot be swapped between purposes. Client ID and exact redirect URI are pinned in each attempt. Codes and access tokens never persist. A trusted future callback page must submit code/state with the initiating owner's session; this backend does not supply that page or mobile deep-link handling.

One transaction consumes state/verifier and marks EXCHANGING before Google is called. Completion rechecks the initiating actor, owner access, expiry and state after the call. Concurrent completion, disconnect or revoked ownership cannot install a late credential in the tested race cases. Lost provider responses or database commits are terminal for that attempt: fresh consent is required. Five starts per tenant per 15 minutes bound request volume, serialized by a tenant advisory lock. Connected credentials carry no promise of ongoing provider health or destination access.

Local disconnect erases local credential/state material; it does not call Google's revocation endpoint or delete remote data. Explain this distinction in client setup and direct users to Google Account permissions for grant removal. Run privileged `db:cleanup:google` every 15 minutes to wipe expired pending material and delete unreferenced FAILED/DISCONNECTED metadata after 30 days. Connected credentials persist until disconnect/tenant deletion; immutable destinations retain referenced connection metadata after credential deletion. Configure backup retention and key rotation before production, and exclude authorization URLs, codes, state, token requests and envelopes from access logs, tracing and model context. Integration tests use synthetic tenants and mocked Google transport; no live credentials or provider calls are used.

Spreadsheet inspection and destination creation require owner access in both HTTP and forced row policies. The backend checks same-tenant connection ownership, local status, pinned OAuth client ID and scope before decrypting. Client data cannot supply provider endpoints, credentials, titles or dimensions. Fixed Drive/Sheets metadata endpoints validate file identity, edit capability, MIME type, trashed state and grid tab identity without reading cells. These observations do not prove future cell write access or Google file ownership. Immutable selection rows preserve actor/time and numeric tab ID; published runs must recheck current provider access and schema before effects.

Sheets delivery requires a separate opt-in flag. Binding/dispatch/reconciliation and job authorization APIs check owner access; tenant members can read their order's safe ledger projection, and the Builder worker has no ledger grants. Destination and expected row are immutable. The row is derived from the retained confirmed intent, and source totals are revalidated. Preparation and connection leases have 120-second bounds and UUID fences. Header/operation checks read only the selected tab's A:L projection, within 1,000 grid rows and a 64 KiB response limit. RAW writes preserve literal customer text; FORMULA reads do not substitute computed results for operation evidence. Spreadsheet contents are untrusted observations, never instructions or configuration.

DISPATCHED commits before the single append attempt. Database guards preserve that attempt identity/timestamp and prevent re-queuing it; completed rows cannot be updated by runtime row policies. Provider errors or lost local acknowledgement persistence remain uncertain, and reconciliation is read-only. No matching row does not authorize a retry. Disconnect/authorization revocation cannot recall a request that already crossed the dispatch boundary. A known receipt can be stored after local disconnect if the owner and attempt fence still permit it. Model-generated tools cannot invoke manual routes or enqueue work without an owner session. There is no forced replay, destination reassignment or remote deletion endpoint. Ledger previews contain order personal data and cascade on tenant deletion; remote projections and backups require separate production deletion/retention policies. Serial synthetic integration tests temporarily revoke the acknowledgement column grant to exercise a failed save, restore it in finally, and verify recovery without another append.

The separate Sheets worker is NOLOGIN until provisioned, requires explicit configuration and rejects other runtime roles. It reads cross-tenant queue metadata for scheduling but cannot create jobs or alter authorizations. Job-scoped forced policies allow only the pinned delivery/destination/credential under a RUNNING, unexpired lease and current requesting-owner membership. It has no sessions/users/orders/chat grants or OAuth state/verifier column grants. Authorization functions are SECURITY INVOKER with a fixed search path, not privileged bypasses. Every execution transaction locks/checks the job fence, sets transaction-local context and rechecks membership. Cancellation, reclaimed leases and owner revocation invalidate data access and pre-dispatch actions. Queued authorization and manual dispatch remain separate; cancellation affects only the job's correlated attempt. Post-dispatch uncertainty remains terminal for automatic delivery. Busy/quota deferrals do not invoke the provider; other failures block rather than retrying network effects. Process shutdown drains a bounded in-flight operation. Protect worker login/vault keys and isolate deployment secrets; direct SQL under a worker login is trusted service access capable of executing existing valid job authorizations. Queue metadata retains actor IDs and cascades with the delivery/tenant; define production retention and backup policy before real onboarding.

Refresh and inspection share a bounded per-connection database lease. HTTP runs outside transactions. Fenced checks before credential rotation and final responses prevent stale results from being saved or exposed after tested disconnect, ownership and lease-expiry races. A rotated refresh token is encrypted before further reads; temporary access tokens remain in server memory. Disconnect clears the lease. Cleanup matches the fence, so an old request cannot release a replacement lease. Provider failures are safe errors and checks are not automatically retried; a lost rotated-token response may require reconnection. The per-connection limit is 20 checks per 15 minutes and includes failed checks. Existing-selection replays make no provider calls. The Builder worker has no destination privileges. Destination snapshots contain business metadata and remain until privileged tenant deletion; configure production retention/export and backups accordingly.
