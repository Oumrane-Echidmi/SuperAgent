# Identity slice: trust boundaries and limits

HTTP bodies, bearer headers and tenant IDs are untrusted. Strict Zod schemas bound fields; SQL values use parameters. The API derives user identity only from a live session digest, then sets transaction-local `app.user_id` on one pooled connection. Tenant context is never accepted from a client header. PostgreSQL policies restrict tenant reads, membership reads, and profile reads/writes. Runtime SQL credentials are trusted service credentials, never client credentials: arbitrary SQL access could set application context directly.

Migrations run with `ADMIN_DATABASE_URL`. The API uses `DATABASE_URL` as the non-owner `superagent_app` login, which has no superuser/BYPASSRLS privileges or role memberships. Startup rejects privileged/owner credentials. The migration role is deliberately privileged and must never serve HTTP. Policies are forced on tenant tables, and grants exclude schema changes, tenant deletion and membership mutation. Platform identity tables (users, sessions and auth counters) are available to the trusted backend for credential verification, not tenant API queries. Responses expose explicit field allowlists.

Abuse cases covered by tests include guessing another tenant's UUID, injecting membership claims, staff editing owner fields, reusing expired/revoked tokens, leaking pooled context, and concurrent rate-limit increments. Invalid credentials return a generic response; unknown accounts perform a dummy scrypt derivation. Account registration conflicts may reveal that an address is registered. Email ownership verification is not implemented; do not expose signup publicly yet.

Passwords use salted scrypt (N=32768, r=8, p=3, 64-byte output). Opaque 256-bit bearer sessions expire after 24 hours. Only SHA-256 token digests persist. Authentication endpoints share PostgreSQL rate counters and each process caps concurrent scrypt derivations at four. The server serves no cross-origin browser credentials and does not enable CORS. Responses use no-store on identity routes, nosniff, frame denial and restrictive CSP. Terminate HTTPS before any public deployment and configure HSTS on that HTTPS boundary.

Data classification: email is personal data used for login; password hashes and session digests are sensitive authentication data; tenant name and profile text can contain business or personal data supplied by an owner. Do not put customer messages or payment data in these fields. Auth counter keys are SHA-256 hashes of IP/email and retained for the active 15-minute window plus cleanup lag. Sessions persist until expiry/revocation plus cleanup lag. Run the cleanup command every 15 minutes. Account/profile data lasts until the development account is removed; no public retention/deletion claim is made by this slice. Before onboarding real shops, implement verified account recovery, deletion/export, explicit retention, audit events, backup retention/recovery and production TLS/proxy controls.

Local database volume persists across container restarts. Never use production data for the integration suite. The suite removes only its generated fixtures; it does not drop schemas or truncate tables.
